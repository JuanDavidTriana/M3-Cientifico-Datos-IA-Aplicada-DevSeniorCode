1De notebook a producción

Un modelo que "funciona" en un notebook y un modelo listo para producción son cosas distintas. En el notebook hay GPU dedicada, tiempo ilimitado y una sola petición a la vez. En producción hay presupuesto de milisegundos, memoria limitada y miles de peticiones concurrentes.

2Técnicas de optimización de modelos

2.1 Pruning

Elimina (pone en cero) los pesos con menor aporte a la predicción, generando una red más dispersa.

Red densa: Red podada: ●───●───● ●───●───● │╲ ╱│╲ ╱│ │ │ │ │ ╳ │ ╳ │ ───▶ │ │ │ │╱ ╲│╱ ╲│ │ │ │ ●───●───● ●───●───● (todas las conexiones) (solo conexiones relevantes)

A mayor sparsity objetivo, menor tamaño, pero mayor riesgo de perder precisión si se poda de forma agresiva.

2.2 Quantization

Reduce la precisión numérica de los pesos (normalmente de float32 a int8 o float16), reduciendo tamaño y, en muchos casos, acelerando la inferencia en CPU.

TipoPrecisiónReducción típicaCuándo usarla
Dynamic rangeint8 pesos / float32 activaciones~4xPunto de partida, sin dataset de calibración
Float16float16~2xHardware con soporte float16
Full integer (int8)int8 pesos y activaciones~4xEdge / microcontroladores, requiere calibración
QAT (aware training)int8 simulado en entrenamiento~4xCuando post-training pierde demasiada precisión
Analogía Es como comprimir una foto a JPEG: el archivo pesa una fracción del original y, para la tarea, la diferencia es casi imperceptible.

2.3 Knowledge Distillation

Un modelo pequeño (student) se entrena para imitar las predicciones de un modelo grande ya entrenado (teacher), aprendiendo de la distribución de probabilidades completa (soft labels) en vez de solo la etiqueta correcta.

Teacher

Modelo grande, ya entrenado, genera predicciones "suaves"

Student

Modelo pequeño, se entrena desde cero imitando al teacher

Resultado

Modelo compacto con desempeño cercano al original

2.4 Comparación resumen

Técnica↓ Tamaño↓ LatenciaRequiere reentrenarComplejidad

¿Por qué no servir el .h5 directamente? Acopla el servicio a tener TensorFlow completo instalado (cientos de MB), con arranque más lento y sin las optimizaciones de un runtime especializado en inferencia.

4Patrones de despliegue

Batch

Procesa grandes volúmenes periódicamente, sin respuesta inmediata (ej. scoring nocturno).

Online / REST API usado en esta clase

Responde a peticiones individuales en tiempo real.

Edge

El modelo corre en el dispositivo del usuario, sin red.

Streaming

Procesa eventos continuos de un stream (ej. detección de fraude en vivo).

5Servir el modelo con FastAPI

FastAPI valida datos con Pydantic, genera documentación interactiva en /docs y es rápido de escribir. El modelo se carga una sola vez al iniciar la aplicación, nunca dentro del endpoint.

from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI(title="Servicio de inferencia")

class PredictionRequest(BaseModel):
    image: list  # matriz de píxeles normalizada

@app.get("/health")
def health():
    return {"status": "ok"}

@app.post("/predict")
def predict(request: PredictionRequest):
    # cargar modelo una sola vez al iniciar la app
    # ejecutar inferencia
    return {"clase": "sneaker", "confianza": 0.94}

7SSH y archivos .env

7.1 SSH — acceso remoto seguro

SSH (Secure Shell) es el protocolo que permite conectarse y ejecutar comandos en un servidor remoto de forma cifrada. Es la puerta de entrada a cualquier máquina en la nube y la base de casi todo despliegue: conectarse a una VM, hacer git push, copiar un modelo con scp, o construir una imagen en un host remoto.

Tu máquina Servidor remoto ┌─────────────────┐ ┌─────────────────┐ │ Llave PRIVADA │ nunca viaja │ Llave PÚBLICA │ │ (id_ed25519) │ por la red │ (authorized_keys)│ └─────────────────┘ └─────────────────┘ │ │ └──────── desafío cifrado ───────────────┘ (solo quien tiene la privada puede responder correctamente)
Analogía La llave pública es un candado que instalas en la puerta del servidor; la llave privada es la única que lo abre y nunca sale de tu bolsillo. Cualquiera puede ver el candado, solo tú puedes abrirlo. 
# Generar un par de llaves (una sola vez)
ssh-keygen -t ed25519 -C "tu_correo@ejemplo.com"

# Copiar la llave pública al servidor
ssh-copy-id usuario@servidor.ejemplo.com

# Conectarte
ssh usuario@servidor.ejemplo.com

# Copiar el modelo optimizado al servidor
scp modelo_optimizado.tflite usuario@servidor:/ruta/destino/

# Ejecutar un comando remoto sin sesión interactiva
ssh usuario@servidor "docker compose up -d"
Buenas prácticas Autenticarse siempre con llaves (nunca contraseña), proteger la llave privada con passphrase, no compartirla ni subirla a un repositorio, usar ~/.ssh/config para no repetir host/usuario, y rotar/revocar accesos cuando alguien deja el equipo.

7.2 Archivos .env — configuración separada del código

Un .env es un archivo con pares CLAVE=valor que contiene la configuración de un entorno: rutas, puertos, credenciales, API keys. La regla central: el código nunca debe tener valores hardcodeados que cambien entre entornos o que sean secretos.

# .env
MODEL_PATH=/app/model/modelo_optimizado.tflite
LOG_LEVEL=INFO
API_KEY=sk-xxxxxxxxxxxxxxxx
Problema sin .envSolución con .env
Credenciales hardcodeadas, visibles en el historial de gitLos secretos viven fuera del repositorio
El mismo código no sirve para dev/staging/producciónCada entorno tiene su propio .env
Cambiar config implica modificar y redeployar códigoBasta con cambiar el .env y reiniciar

El proyecto 2 de esta clase ya aplica esta idea: app/model_utils.py lee os.environ.get("MODEL_PATH", ...), para poder sobreescribir la ruta del modelo sin tocar el código.

# Docker
docker run --env-file .env -p 8000:8000 clase02-inference-api

# docker-compose.yml
services:
  modelo-optimizado:
    build: ./servicio_optimizado
    env_file:
      - .env
Regla de oro El .env con valores reales nunca se sube al repositorio (va en .gitignore). Se versiona un .env.example con las claves esperadas, sin valores sensibles.

8Métricas de despliegue

MétricaQué mideCómo se calcula en el laboratorio
Tamaño del modeloPeso en disco del artefactoos.path.getsize() sobre .h5 vs .tflite
LatenciaTiempo de una inferencia individualPromedio de N llamadas cronometradas
ThroughputPeticiones atendidas por segundoN peticiones / tiempo total
PrecisiónCalidad de las prediccionesAccuracy en el set de prueba antes/después de optimizar

El objetivo nunca es optimizar a ciegas: siempre se compara lo ganado en tamaño y latencia contra lo perdido en precisión.
